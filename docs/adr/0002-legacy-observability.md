# ADR-0002: Observe legacy requests through a shared, allowlisted telemetry contract

- Status: Accepted for the legacy baseline; cross-runtime routing verification pending.
- Story: MOD-002
- Recorded: 2026-11-09

## Context

Operators need request ownership, latency and functional evidence during migration. The legacy
application remains Java 8, Struts and Hibernate 3.5. It has no REST business API. Existing
request IDs and exception logging cover failures only. Exception messages and database errors
can contain submitted credentials, so adding JSON around existing throwable output is unsafe.

## Options

1. Add an agent and hosted telemetry stack. This introduces a separately operated dependency
   before a replacement or routing layer exists.
2. Add a small in-process event store, structured logging, cumulative histograms and an
   administrator dashboard, with a shared export contract. This provides a runnable baseline
   without changing business behavior, but requires explicit retention and aggregation limits.

## Decision

Choose option 2. `Telemetry` records request completions, transaction lifecycle completions,
unexpected failure types and readiness results. Its fields are an allowlist; request bodies,
queries, headers, cookies, actor names, record contents and throwable messages are excluded.
Incoming paths become known `Routes` constants or `other`. Duration uses `System.nanoTime()`;
timestamps use UTC. Transaction timing starts before session acquisition and finishes after
commit/rollback/close. An error outcome means the lifecycle failed, not proof of rollback:
cleanup can fail after commit. Instrumentation never retries or changes transaction ownership.

The HTTP filter sets `X-Request-ID` and `X-Implementation: legacy` on original requests,
including security redirects/rejections. IDs are server-generated by default. Deployments can
enable `trustRequestId` only behind a proxy that overwrites that header with canonical UUIDs
and prevents direct access. Thread-local context is removed in `finally`. Background work uses
`background` correlation. No implementation claim supplied by a client is accepted.

Unexpected failures are logged once with exception type only. The filter gives the servlet
container a generic exception without the original cause, preventing a second, unsanitized
container log. Services retain their original exceptions and transaction semantics. Expected
business corrections remain presentation concerns; a 200 response with an expected validation
message is a completed HTTP request. A handled unexpected exception remains an error outcome
even if Struts renders it with status 200.

`/operations.do` and its exports run through the existing security filter, including active
account/role refresh, then require ADMIN. The dashboard renders values with `textContent` and
can import another implementation's snapshot locally. It does not upload imported data.
`/health/live` is database-independent; `/health/ready` performs `SELECT 1` through the real
transaction template, with a three-second statement timeout. Probes return minimal JSON;
deployments must restrict these public probe paths to monitoring networks. Pool acquisition
and initial SessionFactory creation use deployment connection timeouts, not the SQL timeout.

## Retention and ownership boundaries

The local dashboard retains the latest 1,000 events per application process, including static
requests, probes and operations requests. Histograms are cumulative until redeployment and
have finite kind/operation/outcome labels, never request IDs. The dashboard's p50/p95 values
describe only requests in the loaded snapshots. Refresh is manual to avoid self-polling noise.
Configure a dedicated JUL handler for durable JSON lines and ship them using the deployment's
log collector before claiming complete historical request coverage. Multi-node deployments
must collect every node's logs; the local dashboard is not a distributed trace backend.

The replacement must produce the same fields with its own implementation/version. MOD-003
owns proxy routes, trusted ID generation and rollback. A response's implementation header and
the correlated completion event are evidence of who actually handled the request. A route's
configured destination alone is not evidence. No replacement traffic is simulated to claim
cross-runtime acceptance.

## Validation

Unit tests cover trusted/untrusted/invalid IDs, safe paths, thread cleanup, lifecycle failures,
bounded history, histograms, probe failure and administrator enforcement. Browser integration
tests deploy the real WAR and verify probes, redirects, administrator access, dashboard loading,
exports, credential canaries and authentication transaction events. Existing characterization
and browser workflow suites continue to establish functional equivalence.

Before a migration is accepted, run identical fixture scenarios against both implementations;
retain snapshots/check results and find each routed request by ID with its actual owner.
Repeat after switching a route back. PostgreSQL and full Java EE deployment checks remain
environment-specific.

## Rollback

Leave `trustRequestId=false` when no trusted proxy exists. Roll back the instrumentation WAR
as a unit if necessary; no schema or business-data changes are introduced. Redeployment clears
local events/metrics, so retain collected logs first. Restrict or disable external probe routes
at the ingress independently. Dashboard access does not grant workflow write permissions.
